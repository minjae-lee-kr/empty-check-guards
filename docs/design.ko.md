# 설계, 계약과 한계

[개요](../README.ko.md) · [English](design.md)

## 해결하려는 문제

밖에서 보면 서로 다른 세 가지 상황이 같아 보일 수 있습니다.

| 실제로 일어난 일 | 발견 사항만 나열하는 보고서에 보이는 내용 |
|---|---|
| 검사를 실행했고 문제를 발견하지 못함 | 발견 사항 0개 |
| 검사 대상이 0개였음 — 잘못된 glob, 빈 조회 구간, 잘못된 경로 | 발견 사항 0개 |
| 검사를 실행하지 않았거나 보고 전에 프로세스가 종료됨 | 아무것도 없음. 발견 사항만 나열하는 보고서로는 0개와 구분할 수 없음 |

첫 번째 상황도 필요한 검사 범위를 충족했을 때만 통과로 판단할 수 있습니다. 이 저장소는 나머지 두 상황을 드러내는 세 가지 장치를 보여 줍니다.

1. **최소 검사 범위.** 끝까지 검사한 대상이 예상보다 적거나 너무 많이 건너뛴 실행은 그대로 통과할 수 없습니다. 별도 종료 코드를 가진 *inconclusive*로 판정합니다.
2. **이유가 남는 건너뛰기.** 대상을 건너뛰려면 이유가 필요합니다. 이유는 보고서에 남고, 건너뛴 대상은 검사 범위 계산에 반영합니다.
3. **판정에 도달했을 때만 기록하는 하트비트.** 별도의 감시 작업은 하트비트가 없거나 오래됐을 때 이를 경보 조건으로 판단합니다.

빈 디렉터리를 검사하면 다음과 같이 출력합니다.

```
[INCONCLUSIVE] manifest policy: no legacy-token auth: scanned 0 of 0 discovered, skipped 0, findings 0 (0 violation, 0 unverifiable)
  coverage: no targets were discovered
exit code: 2
```

두 검사 예제는 `--json`으로 요약 객체를 출력할 수 있습니다. 파이프라인은 로그 문자열을 파싱하지 않고 `status`, `coverage`, `findings[].kind`, `override`를 읽을 수 있습니다.

세 CLI 모두 알 수 없거나 반복된 옵션, 누락된 값, 불필요한 위치 인자를 종료 코드 2로 거부합니다. 하트비트 옵션은 `touch`와 `check` 각각에 맞게 제한합니다. `-`로 시작하는 경로를 위치 인자로 전달할 때는 앞에 `--`를 붙입니다. 오타 때문에 실제 실행하는 정책이 조용히 달라져서는 안 됩니다.

## 설계

핵심 구현은 [`src/guards.js`](../src/guards.js)의 `CheckReport` 클래스와 하트비트를 다루는 몇 가지 순수 함수입니다. 예제는 이 핵심을 호출하는 얇은 실행 코드입니다.

### 결과 계약: found, covered, next

`CheckReport`는 검사 범위에 각 대상을 한 번만 계산합니다. 대상은 scanned, skipped, unverifiable 중 하나로 기록하며, 같은 id를 이 역할들에 중복 등록할 수 없습니다. violation은 이미 scanned로 기록한 대상에 추가합니다. 대상 소스의 오류는 개별 대상과 분리해 기록합니다.

| 호출 | 의미 |
|---|---|
| `scanned(id)` | 대상을 끝까지 검사함 |
| `skipped(id, reason)` | 의도적으로 검사하지 않음. 이유가 필수 |
| `finding(id, message)` | `kind: violation`(기본값): 이미 검사한 대상이 정책을 위반함. `id`를 검사하지 않았다면 예외 발생 |
| `finding(id, message, { kind: 'unverifiable' })` | 대상은 있지만 검사할 수 없었음. 이 호출이 대상 자체를 등록하므로 scanned나 skipped에는 포함하지 않음 |
| `sourceError(message)` | 대상 소스를 읽을 수 없음 — 디렉터리 없음, 조회 실패 등. 대응할 담당자가 다르므로 “읽을 수 있지만 비어 있음”과 구분 |

`finish()`는 다음을 보고합니다.

- **found**: 발견 사항과 각 항목의 종류
- **covered**: `scanned`, `discovered`(scanned + skipped + unverifiable), `coverage.reasons`. 검사 범위가 충분하면 이유 목록은 비어 있음
- **next**: `status`, `exitCode`, 예외 승인이 있으면 `override`

### 판정

| 조건 | 상태 | 종료 코드 |
|---|---|---|
| 검사 범위와 관계없이 발견 사항이 있음 | fail | 1 |
| 발견 사항은 없지만 검사 범위가 부족함 — 소스 오류, 발견한 대상 0개, `scanned < minTargets`, 건너뛴 비율이 `maxSkipRatio` 초과 | inconclusive | 2 |
| 발견 사항이 없고 검사 범위가 충분함 | pass | 0 |

발견 사항을 우선합니다. “검사 범위가 부족했다”는 이유로 확인한 위반을 숨기지 않으며, 부족한 범위도 함께 보고합니다. 검사 범위가 부족해도 발견 사항이 inconclusive로 바뀌지 않는지 회귀 테스트로 확인합니다.

`inconclusive`를 `fail`과 구분한 것은 의도한 선택입니다. 위반을 발견한 검사는 해당 대상의 담당자가, 검사할 대상이 없었던 실행은 자동화 담당자가 확인해야 합니다. 종료 코드가 직접 전달 경로를 정하지는 않지만, 이를 구분할 수 있게 합니다. 모든 0이 아닌 종료 코드를 실패로 처리하는 CI에서는 둘 다 빨간색으로 표시됩니다. 별도 전달 경로를 정하는 코드는 `--json` 출력이나 로그를 읽어야 합니다.

`minTargets`의 기본값은 1이며 생성자는 0을 거부합니다. “대상이 0개인 것이 맞다”는 판단은 설정값 대신 아래의 예외 승인으로 남깁니다. 환경이 *평소에도* 비어 있다면 매번 예외를 승인하는 방식은 적절하지 않습니다. 예상한 대상 목록과 관측한 목록을 비교해야 하며, 이 저장소는 그 기능을 구현하지 않습니다.

### 예외 승인과 신뢰 범위

아직 아무것도 배포하지 않은 새 환경처럼 대상이 0개인 것이 맞을 때도 있습니다. `finish({ override: { by, reason } })`와 `--override-by / --override-reason` 옵션은 이런 경우를 위한 기능입니다.

1. 이름과 사유가 모두 필요합니다. 익명 예외 승인은 거부합니다.
2. 예외 승인은 inconclusive 실행에만 적용합니다. 발견 사항이 있는 실행에는 적용할 수 없습니다. CLI는 `override refused`를 출력하고 종료 코드 1을 유지합니다.
3. 요약과 로그의 **상태는 `inconclusive`로 유지**합니다. 종료 코드만 0으로 바뀌며, 예외 승인은 허용한 검사 누락과 함께 기록합니다.

예외 승인에는 **호출자가 주장한 내용**을 남깁니다. `by`는 호출자가 전달한 문자열입니다. CI 시나리오에서는 파이프라인의 실행 주체 변수를 전달하므로 그 파이프라인의 인증 수준만큼만 신뢰할 수 있습니다. 승인을 검증하려면 승인자를 인증하고 해당 실행·예외와 승인을 연결하는 외부 통제가 필요합니다. 이 도구는 무엇을 허용했는지와 그 결정을 함께 기록합니다.

### 하트비트

`heartbeatRecord`는 작업의 **마지막** 단계에서, 실행 결과가 `pass`나 `fail`일 때만 기록합니다. 검사 범위가 부족한 fail도 포함하므로 “가장 최근에 판정에 도달한 실행”을 뜻하며, “모든 것을 검증했다”는 뜻은 아닙니다. inconclusive는 예외 승인을 받았어도 하트비트를 갱신하지 않으며, 중간에 프로세스가 종료된 경우도 갱신하지 않습니다. 감시 작업은 최근 판정이 없다는 사실을 감지합니다. 작업이 멈췄거나, 계속 실행되지만 정해진 시간보다 오래 inconclusive만 반환하는 경우 모두 확인이 필요합니다.

`assessHeartbeat`는 기록과 현재 시각만으로 결과를 정하는 순수 함수입니다. 따라서 stale과 fresh의 경계를 초 단위로 검증할 수 있습니다. 미래 시각의 기록은 fresh가 아니라 `invalid`입니다.

저장된 기록에는 비어 있지 않은 작업 이름, `pass` 또는 `fail` 판정, 유효한 UTC 시각(`YYYY-MM-DDTHH:mm:ss[.sss]Z`)이 필요합니다. 최근 시각 하나만으로 판정에 도달한 실행이라고 볼 수는 없습니다. 호출자가 전달하는 `now`는 유효한 `Date`여야 하며, 허용하는 경과 시간은 유한한 양수여야 합니다. 이 검사는 형식이 잘못된 데이터를 거부하지만 작성자를 인증하거나 예상한 작업의 기록인지 확인하지는 않습니다.

`touch`는 대상 파일 옆에 고유한 이름의 임시 파일을 쓰고 flush한 뒤 기존 기록을 교체합니다. 임시 파일 쓰기나 이름 변경이 실패하면 이전 기록을 유지하고, 가능하면 임시 파일을 정리합니다. 일반적인 쓰기 실패로 마지막 유효한 하트비트가 잘리는 것을 피하기 위한 방식입니다. 분산 잠금이나 전원 장애 이후의 내구성 보장이 아닙니다. 동시에 쓰면 마지막으로 교체한 기록이 남으며, 파일시스템 동작에도 영향을 받습니다.

검사 스크립트가 직접 하트비트를 쓰지는 않습니다. [CI 연결 예제](../examples/ci-manifests.js)는 정해진 설정 파일 검사 CLI를 실행하고, 그 자식 프로세스의 완전한 JSON 결과를 검증한 뒤 하트비트를 기록합니다.

```bash
node examples/ci-manifests.js ./manifests ./nightly.json
```

Bash `-e`를 쓰는 CI 단계에서도 한 명령으로 실행할 수 있습니다. fail 판정에 도달한 검사는 연결 프로세스가 종료 코드 1을 반환하기 **전에** 하트비트를 기록합니다. 반면 `node check.js; code=$?`는 실패 시 즉시 종료하는 설정에서 변수 대입 전에 셸이 끝날 수 있습니다. [GitHub의 기본 셸 설정](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsshell)도 이 동작을 사용합니다.

더 근본적으로, **종료 코드 1만으로 fail 판정을 확인할 수는 없습니다.** Node는 초기화 오류로 검사 대상을 읽기도 전에 1을 반환할 수 있습니다. 연결 예제는 같은 자식 프로세스의 stdout을 메모리에서 수집하고, 완전한 JSON 보고서 하나를 파싱해 검사 식별자, 대상 수, 검사 범위 정책, 판정과 예외 승인 필드를 확인합니다. 보고서와 프로세스 종료 코드도 일치해야 합니다. 실행 시작 오류, 강제 종료, 잘린 출력, 판정·종료 코드 불일치는 통합 오류(종료 코드 2)이며 하트비트를 쓰지 않습니다. 이전 보고서 파일은 읽지 않습니다. Windows에서는 강제 종료가 POSIX 신호 대신 숫자 종료 코드로 보일 수 있지만, 완료된 보고서가 없으면 마찬가지로 거절합니다.

유효한 fail 보고서를 출력한 뒤 프로세스가 비정상 종료돼도 종료 코드는 1일 수 있습니다. 이 고정 CLI의 완료된 판정은 stdout의 JSON과 **빈 stderr**로 정의합니다. 따라서 JSON과 종료 코드가 맞아도 예상 밖 stderr가 있으면 거절합니다. 보고서 출력 뒤의 예외나 파이프 오류도 여기에 해당합니다. 런타임 경고 역시 보수적으로 거절하며, stderr 문구 중 무엇이 무해한지 추측하지 않습니다.

기존 `--min`, `--override-by`, `--override-reason` 옵션을 사용할 수 있습니다. 예외 승인된 inconclusive는 종료 코드가 0이어도 하트비트를 그대로 둡니다. 검증한 pass·fail은 작업명 `manifest-policy`와 이번 연결 실행의 ID를 기록합니다. 저장이 실패하면 실제 검사 판정은 결과에 남기고 통합 오류 2를 반환하며, 하트비트는 `unconfirmed`로 표시합니다. 교체가 성공했다거나 이전 바이트가 반드시 남았다고 단정하지 않습니다. 하트비트 도구의 일반적인 쓰기 실패 보존 규칙은 그대로 적용됩니다.

자식 프로세스는 같은 폴더의 정해진 CLI입니다. 임의 실행 파일이나 셸을 지정하는 옵션은 없습니다. 출력 스트림별로 1 MiB, 자식 실행에는 30초 제한을 두며 한도를 넘은 실행을 완료된 판정으로 취급하지 않습니다. JSON 결과는 `check`, `child`, `heartbeat`를 구분합니다. 신뢰하는 검사기의 결과 규약을 검증하는 예제이며 악의적인 프로세스나 실행 환경의 진실성을 증명하지 않습니다. 설정 파일을 독립적으로 다시 검사하지도 않습니다.

### 실패 경로

| 상황 | 동작 | 이유 |
|---|---|---|
| 디렉터리가 없거나 읽을 수 없음 | `sourceError`, inconclusive, 종료 코드 2 | “디렉터리가 있지만 비어 있음”과 담당자가 다르므로 이유도 구분 |
| 디렉터리는 있지만 일치하는 대상이 없음 | `no targets were discovered`, inconclusive, 종료 코드 2 | glob이 더 이상 대상을 찾지 못하는 경우 |
| 설정 파일을 파싱할 수 없거나 유효한 `auth.mode` / 건너뛰기 사유가 없음 | `unverifiable` **발견 사항**, fail | 검사할 수 없는 대상을 정상으로 볼 수 없음. 건너뛰기로 처리하면 검사 범위가 조용히 줄어듦 |
| 이유 없이 건너뜀 | 호출 시 `TypeError` | 이유 없는 검사 누락을 막기 위한 보고서 |
| 같은 대상 id를 scanned, skipped, unverifiable로 중복 등록 | 호출 시 `Error` | 같은 대상을 두 번 반환하는 것은 상위 입력의 버그이며 추가 검사 범위가 아님 |
| 검사하지 않은 대상에 위반을 등록 | 호출 시 `Error` | 검사하지 않은 대상은 판정할 수 없음 |
| CLI의 본문에서 잡아 처리한 오류 | 종료 코드 2 | 끝나지 않은 실행은 “확인되지 않음”이며 0이 될 수 없음 |
| 보호된 본문에 들어가기 전 초기화 실패 | 보고서 없이 1로 끝날 수 있으며 연결 예제는 거절 | 프로세스 실패를 완료된 fail 판정으로 바꾸면 안 됨 |
| 외부에서 프로세스를 종료 | 이 도구가 정한 종료 코드 없음 | 하트비트로 확인해야 하는 공백 |
| 오류율 버킷의 요청이 0건 | 이유와 함께 건너뜀 | 요청이 없으면 오류율을 정의할 수 없음 |
| 표본 형식, 건수 또는 수치 정책이 잘못됨 | 예외 발생, CLI 종료 코드 2 | 잘못된 근거를 요청 없는 버킷이나 정상 오류율로 바꾸면 안 됨 |
| 하트비트 파일이 없음 | `missing`, 종료 코드 2 | 기록이 없다는 것은 최근 기록이 있다는 뜻이 아님 |
| 하트비트를 읽을 수 없거나 미래 시각임 | `invalid`, 종료 코드 2 | 시계 차이나 수정된 파일을 정상으로 판단하면 안 됨 |

### 오류율 검사의 정확한 기준

임계치는 **버킷별로** 적용합니다. 어느 버킷이든 오류율이 1 %를 넘으면 위반이므로 짧은 오류 급증이 나머지 조용한 시간에 묻히지 않습니다. 한 시간 전체의 `sum(errors) / sum(requests)`를 계산하는 방식이 아닙니다. 이 예제는 12개 중 최소 11개 버킷을 평가할 수 있어야 하므로, 버킷 하나가 없거나 비어 있는 것은 허용합니다. 누락된 버킷에 오류가 있었을 수도 있습니다. 이 허용 범위는 선택한 절충이며 보장이 아닙니다. 중복 버킷 id는 예외로 거부합니다. 버킷은 개수를 셀 뿐, 시각이 의도한 구간에 속하는지는 검사하지 않습니다.

표본에는 비어 있지 않은 문자열 id와 `0 <= errors <= requests`를 만족하는 안전한 정수 범위의 건수가 필요합니다. 숫자 문자열, 음수, 유한하지 않은 값, 소수는 거부합니다. 설정도 숫자 자동 변환을 허용하지 않습니다. 문법상 올바른 JSON이라고 해서 유효한 검증 근거인 것은 아닙니다.

## 시나리오 스크립트로 확인하는 범위

[`scripts/scenarios.mjs`](../scripts/scenarios.mjs)는 fixture를 임시 디렉터리에 복사하고, **호출과 호출 사이에** 입력을 바꾸며 실제 CLI를 실행합니다. 입력 존재 → 삭제 → 빈 상태로 재생성 → 예외 승인 순서로 진행한 뒤, 발견 사항에 대한 예외 승인 거부, 요청 없는 조회 결과, 기록 없는 감시 작업도 확인합니다. 단계마다 종료 코드를 검사하고, 그것만으로 성질을 확인할 수 없으면 출력이나 파일 상태를 검사합니다. 예외 승인 후 `[INCONCLUSIVE]`와 `OVERRIDE recorded`가 남는지, 발견 사항에 `override refused`가 표시되는지, 거부된 `touch`가 하트비트 파일을 만들지 않는지 확인합니다. 모든 예상과 일치하면 시나리오 실행기 자체는 0으로 종료합니다. 실제 파이프라인 단계를 실패시키려면 사용하는 쪽에서 검사 CLI의 종료 코드를 전달해야 합니다. Node 하위 프로세스 API를 직접 사용하고 자체 임시 디렉터리를 정리하므로 Windows와 Unix에서 같은 계약을 실행할 수 있습니다.

이 시나리오는 *사용자의 파이프라인*을 검증하지는 않습니다. 종료 코드 2가 1과 다른 경로로 전달되는지, `--json` 출력을 보관하는지, 누군가 `OVERRIDE recorded`를 읽는지는 이 도구를 도입한 시스템의 통합 문제입니다. 한 번의 호출이 실행되는 도중 입력이 바뀌는 상황도 다루지 않습니다.

## 관련 기법

세 장치 모두 새로운 기법은 아닙니다. pytest는 “테스트 실패”와 “수집한 테스트 없음”을 종료 코드로 구분합니다. Prometheus에는 데이터가 없는 상태에 경보를 걸 수 있는 `absent()`와 `absent_over_time()`이 있습니다. 정기 작업의 신호가 끊기면 알림을 보내는 dead-man's-switch 서비스도 있습니다. 이 저장소는 세 가지를 함께 실행할 수 있는 작은 형태로 구성하고, 사람이 예외를 허용한 뒤에도 “확인하지 못한 것”이 남는 결과 계약을 보여 줍니다.

## 한계

- **임계치는 예시입니다.** `minTargets`, `maxSkipRatio`, 오류율 1 %, 버킷 12개는 예제 값입니다. 실제 값은 관측한 트래픽과 팀의 허용 범위에 맞춰 정해야 하며, 이를 관리할 담당자가 필요합니다. 대상이 줄었는데 최소 기준을 갱신하지 않으면 평소 실행에도 예외 승인이 필요해집니다.
- **검사 범위는 대상 이름이 아닌 개수로 확인합니다.** 최소 기준이 1이면 어느 대상이든 하나만 검사하면 충족합니다. 건너뛰기 비율 50 %는 두 대상 중 가장 중요한 하나를 건너뛰어도 허용합니다. 필수 대상 목록과의 대조가 다음 장치가 될 수 있지만 여기에는 구현하지 않았습니다.
- **버킷의 완전성도 개수로만 확인합니다.** 오류율 검사는 버킷 수를 세고 중복을 거부하지만, 각 버킷의 시각이 의도한 구간에 속하는지 확인하지 않습니다.
- **결과 전달 경로는 구현하지 않습니다.** 종료 코드 2와 `--json` 요약으로 inconclusive를 구분할 수 있습니다. 이를 일반 실패와 다른 곳에 전달하는 일은 파이프라인의 책임입니다.
- **예외 승인은 기록할 뿐 인증하지 않습니다.** 위의 신뢰 범위를 참고하세요.
- **감시 작업도 하나의 작업입니다.** 감시 작업 자체를 별도로 모니터링해야 합니다. 다른 호스트에서 실행하면 같은 호스트의 장애가 함께 영향을 주는 문제는 피할 수 있지만, 감시 작업 자체가 멈추는 것을 감지하지는 못합니다. 이 저장소는 한 단계의 감시만 다룹니다.

## 다음에 검증할 항목

- **필수 대상.** 전체 개수는 `minTargets` 이상으로 유지하면서 필수 서비스 하나를 제거합니다. 개수만으로 드러나지 않는 누락이 예상 id와 관측 id를 비교하면 드러나는지 확인합니다.
- **버킷의 시간 구간.** 중복 없는 버킷 12개 중 하나를 요청한 시간 밖으로 설정합니다. 개수 기준은 통과하지만 시간 구간 검사가 있어야 이를 발견하는지 확인합니다.
- **에이전트가 보고하는 검사 범위.** 의도한 입력의 일부만 받은 에이전트가 “문제없음”을 보고하게 합니다. 별도로 보관한 전달 입력 기록으로 누락을 드러낼 수 있는지 확인합니다. 이 기록은 어떤 입력을 제공했는지 확인할 뿐, 모델이 그 입력을 올바르게 검사했다는 증거는 아닙니다.
